# Audit and capacity — September 29, 2026

After the pace work (the highlight keeping step with the reciter, [LIVE_FOLLOW_REVIEW.md](LIVE_FOLLOW_REVIEW.md)), the owner asked for anything else worth fixing, then for a test with 10,000 users. Three independent reviews covered the hosted service's security, the livestream (OBS) experience and phone listening; each finding was verified in code, and where marked, by running it. Evidence layers are kept separate: **measured** (run here), **rendered** (seen in Edge), **code** (read), **docs** (platform documentation, not tried on a device). Nothing here has been deployed.

## Capacity: 10,000 users

`npm run load` builds the hosted server exactly as `main.ts` does (corpus, resources, word meanings, Latin reader, credits and links in a temporary directory) in one process, and simulated visitors in another. Visitors arrive like the reader page (visitor cookie, control socket, chapters, one surah) and stay connected; reciters also go through the real audio relay, with a local stand-in for the recogniser replaying five owner recordings of different surahs at recording speed. No provider or payment is called. Measured on this machine (AMD Ryzen 7 7700X, one Node process, which uses one core).

| Load | Server response p50 (p99) | Recogniser result → highlight p50 (p99) |
|---|---|---|
| 10,000 readers connected (arrived in 36 s, 0 errors) | 1 ms (3 ms) | — |
| + 50 reciting | 1 ms (12 ms) | 2 ms (11 ms) |
| + 100 reciting | 1 ms (11 ms) | 3 ms (15 ms) |
| + 150 reciting | 2 ms (21 ms) | 4 ms (22 ms) |
| + 200 reciting | 9 ms (62 ms) | 12 ms (67 ms) |
| + 250 reciting | 628 ms (909 ms): saturated | 359 ms (399 ms) |

Before today's changes the same test saturated at ~60–80 reciters (100 reciting: 206 ms p50, 2.5 s p99; 400: 21 s), and 10,000 readers needed ~970 MB.

- **Reading scales.** A reader's session is 5.1 KB (was 44.5 KB: the Arabic surah-name matcher was rebuilt per visitor; now shared). 10,000 open pages: ~420–560 MB for the whole process, within the $6 server's 1 GB.
- **Reciting is CPU.** ~0.4% of this core per reciter after halving the tracker's cost (the word-similarity check was half of it; decisions byte-for-byte identical on every replay). A shared cloud vCPU is roughly 2.5–3 times slower single-threaded, so the $6 server carries roughly 70–80 reciters at once; the relay's default cap is 60 (`QO_MAX_LISTENERS`), and new listening also waits while the event loop is delayed. Beyond the cap people are asked to try again in a minute; reading is untouched.
- **The recogniser's limit comes first.** Soniox allows 10 real-time streams at once per project and 100 new streams a minute by default ([limits](https://soniox.com/docs/stt/rt/limits-and-quotas)); higher limits are requested in the Soniox Console. Its refusal (429) or an empty balance (402) is now shown as the same wait, or "listening is unavailable", with the set-aside time returned.
- **Then money.** Listening costs about $0.12 an hour of recognition; the sponsored pool held ~30.8 hours. 10,000 people reciting 20 minutes a day would be ~3,300 hours a day. When the pool is empty, listening pauses for everyone and reading continues.
- **Beyond one server:** sessions live in one process, so more than ~200 reciters at once needs several processes with each visitor routed to the same one (sticky by visitor cookie; overlay links by their visitor), or the tracker moved to worker threads. Not built.

## Fixed

### Hosted service (commits f65a1b6, 03e9b4a)

| Finding | Evidence | Fix |
|---|---|---|
| One crafted control message could hold the whole server: recitation in Latin letters was searched across the whole Quran without bound. | measured: a 3.6 KB message froze it 3 s; now 0 ms | Latin runs read 8 words at a time; patterns over 64 letters not searched. |
| No per-page message or byte budget on the control socket; a handler error could escape. | code | Per-page budget (60 messages/s, 64 KB/s, 512 KB burst), per-visitor page cap (8), errors caught. |
| Recogniser results were accepted from any page. | code | Only from a visitor with a relay stream open. |
| Out-of-range audio times pushed the new pace timer past Node's limit, re-firing every millisecond. | measured (a bug in the pace work) | Audio times bounded to one stream; no pace timer beyond 10 s. |
| Visitors could switch the owner's tracker mode (which decides paid decisions) and send unlimited paid requests. | code | Mode ignored in hosted mode; requests limited to 4 per 10 s per page, with a reply. |
| IPv6 visitors were keyed by full address: one /64 was unlimited "networks". | code | IPv6 keyed by its /64. |
| Stalled pages queued messages without end; unauthenticated relay sockets held reciters' places. | code | Sockets past 1 MB buffered let go; overlay connections limited per network; relay sockets awaiting a ticket capped separately. |
| Reading needed a visitor cookie, capped at 30 new per network per hour: the 31st phone on a mosque's Wi-Fi could not open a surah. | code | Reading needs no cookie; the new-visitor limit is 200 an hour. |
| At capacity nothing refused new listening, and the recogniser's own limits surfaced as connection errors. | measured | See *Capacity*. |

### Livestream (commits f65a1b6, 734cfad)

- Hosted overlay links died with their session (30 min after the control page closed, and on every restart or deploy); OBS then showed an error on stream and the look reset. **Code**; now each visitor's link and look are saved, OBS reconnects to the visitor's session, and a refused link leaves the stage empty (never an error in front of the audience).
- Translation pages never turned while reciting (every display change restarted their timer). **Rendered**; fixed.
- Passages re-flowed at their last ayah; word focus showed "Ready to follow" on stream and jumped when meanings appeared; unhide replayed the rise; a dark custom colour hid the frame; credits were hard to read over bright footage; meanings covered the next line. **Rendered**; fixed and checked in 29 overlay renderings.
- Losing the control page left a word highlighted while the reciter moved on. **Code**; the ayah stays, the highlight goes.

### Phones (commits 2b509cb, 8f6979b, 47d64c9)

- iPhones before iOS 18.4 record only MP4/AAC, which the recogniser's real-time API does not list: WebM/Opus where supported, otherwise 16 kHz PCM from an audio worklet. **Docs + browser test with an iPhone user agent; not yet on an iPhone.**
- A mic mute of 5 s (a call, Siri) ended hosted listening. **Measured** with the real SDK against the relay; keepalives are now forwarded.
- Nothing kept the screen on or recovered after it locked. Screen wake lock while listening; recovery on return with a plain notice. **Simulated in Edge; not on a device.**
- A reconnecting control socket lost the stream's place; pages now re-announce it.
- Pages were sent ~6 KB for every recogniser result (~42 KB/s on a phone): now 7.7 KB/s. The phone's highlight no longer waits for batched snapshots. **Measured.**

## Open (needs the owner)

1. **Soniox concurrency.** Check the project's limit in the Soniox Console (10 by default) and raise it before any launch push; set `QO_MAX_LISTENERS` at or below it.
2. **Visitor addresses on the live route.** The app trusts the proxy's `X-Forwarded-For` only with `QO_TRUST_PROXY=1`; the live runtime's setting is unknown here. Without it every visitor shares one address (one daily share, one new-visitor limit, 8 idle pauses block everyone). The server now warns once at startup traffic; `deploy/production.env.example` includes it.
3. **Cookie path (uncommitted owner work in `src/server/app.ts`).** The new `Path=/quran-reader` applies only to new visitors: `/api/me` re-issues a cookie only when none is valid, so existing `Path=/` cookies keep going to all of nurra.org for up to a year. Re-set with the new path and expire the `Path=/` copy.
4. **Live verification.** Phone fixes untested on a real iPhone or Android phone; the overlay not yet loaded in OBS itself; load measured on a desktop, not the $6 server.
